The 5 Digital Fill-Up Forms

These are the old training forms that the current system now serves through the post-approval form workspace. They are still the same core documents, just digitized and reviewed inside the portal.

1. Availment Form Client identity, family or individual project details, income eligibility, commitments, and signatures.
2. Validation Form Eligibility checklist, validator-style details, and participant signature.
3. Mungkahing Proyekto Project rationale, products/services, materials, labor, tools, expenses, and expected sales.
4. Business Plan Marketing, production, organization, and financial planning content.
5. Buhat sa Pagpanumpa Program oath, applicant and co-maker details, dates, and final signatures.

Prototype Workflow

This is the clean version of the current real flow, grouped by role. It follows the behavior already present in the system today, including the hybrid “post-approval” naming used for the old 5 forms.

Applicant

Fill-up and resubmission lane

The applicant does not see all forms by default. They only see the forms opened by the current gate and training codes.

Step A1: Finish core application requirements

The applicant first uploads the required application documents in the applicant portal.

  • These uploads must be reviewed and fully verified first.
  • If not fully verified, the 5 form workspace remains blocked.

Step A2: Open the training-form tracker

Once the gate is open, the applicant can access the tracker page and only the allowed seminar-form codes show up.

  • Unlocked forms can be opened.
  • Unavailable forms stay visible but not clickable.

Step A3: Fill out one of the 5 forms

The applicant opens a form page, enters the requested details, and uploads signatures or attachments where allowed.

  • Save draft changes the task to In Progress.
  • Submit sends the form to reviewer queue as Submitted.

Step A4: Revise if PDO sends it back

If the PDO marks the form as Needs Correction or Rejected, the applicant sees the reviewer note and reopens the same form for revision.

  • Reviewer remarks appear in the tracker and inside the form page.
  • The applicant edits and resubmits the same form.
System

Gate and routing lane

The system decides when tasks exist, which forms are open, and where submissions go next.

Step S1: Verify application gate

The system checks whether the applicant’s required uploads are fully verified.

  • If false, the form API returns blocked state.
  • If true, the workspace beneficiary profile and application-stage tasks are ensured.

Step S2: Read training invite seminar codes

The system looks at the applicant’s training invite and extracts the allowed seminar form codes.

  • This is why one applicant may not see all 5 at once.
  • The current order is Availment, Validation, Mungkahing Proyekto, Business Plan, then Buhat sa Pagpanumpa.

Step S3: Persist payload and status

Draft save stores `form_payload`. Final submit stores payload, task status, and a `post_approval_submissions` record.

  • Draft becomes In Progress.
  • Final submit becomes Submitted.

Step S4: Notify and reflect status

The system pushes the latest status back into the applicant tracker and reviewer queue.

  • Applicant sees new state and remarks.
  • PDO sees the form in the review queue.
PDO

Review and decision lane

The PDO checks submitted fill-up forms through the post-approval review interface or the application review embed.

Step P1: Open review queue

The PDO sees submitted or previously reviewed form tasks in the review queue.

  • The queue includes only the 5 digital forms.
  • Status scope includes Submitted, Needs Correction, Rejected, and Verified.

Step P2: Inspect applicant submission

The reviewer can inspect the applicant’s entries, applicant identity, history, and staff-only review sections.

  • PDO may also upload reviewer-side files or signatures.
  • The latest Admin modal now mirrors this PDO review behavior.

Step P3: Decide the outcome

PDO chooses one review result.

  • Verified if acceptable
  • Needs Correction if the applicant can revise it
  • Rejected if the submission should not proceed

Step P4: Save review and notify

The system updates the task, the latest submission row, and sends the applicant-visible remark back to the applicant portal.

  • Correction and rejection require an applicant-visible remark.
  • Verified closes the loop for that form.
Admin / SW

Oversight and visibility lane

These roles do not fill the forms, but they can monitor the same general lifecycle and review state.

Step O1: Observe applicant readiness

Admin and SW can track whether an applicant has already reached the form-eligible stage.

Step O2: Observe review outcomes

Once forms are submitted and reviewed, the oversight side can see the reflected statuses and applicant progression.

Step O3: Use the same latest form-review pattern

The Admin-side application review modal now follows the newer PDO-style fill-up form review behavior.

Current-system reality: the old 5 training forms are still being served through the post-approval task infrastructure. So the naming is hybrid, but the applicant-to-PDO digital fill-up workflow is already live in that structure.

Status Prototype

This is the simplest way to read the task state transitions for one form in the current system.

Locked

The applicant still cannot use the form because the required application gate or seminar access is not open.

Unlocked

The form is available to open. The applicant may begin filling it up.

In Progress

The applicant saved a draft, but the form has not yet been formally submitted for review.

Submitted

The form is now in the PDO review queue and ready for checking.

Needs Correction

PDO returned the form with a revision note. The applicant edits the same form and resubmits it.

Rejected

The submission did not pass review. The applicant still sees the reviewer remark.

Verified

The form is accepted and effectively complete from the reviewer side.
